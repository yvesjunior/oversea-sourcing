Part 0 · the substrate

The runtime everything else sits on

A modular monolith with physical seams: one codebase, one image, six services on a single VM behind a Cloudflare tunnel. Every module sits behind an interface that could become a network boundary — extraction would be a deploy change, not a refactor.

The pipeline is resume-capable, and that is load-bearing

It reads a request's current status and picks up wherever it rests, so a re-run is safe. On boot and every 60 seconds the sweep re-enqueues anything sitting in received, searching or validating untouched for two minutes — a worker crash, a lost job, a container restart mid-flight all self-heal.

Every transition writes an event row, and the timelines, the activity feed and the dashboard are pure reads of those tables. Nothing recomputes state in order to display it.

No broker, deliberately

pg-boss gives transactional enqueue for free — a request and its job commit together — which RabbitMQ would only match through an outbox pattern, which is a queue in Postgres anyway. pg_dump snapshots state and in-flight jobs together. All enqueues go through one seam, so swapping it later is an adapter rather than a refactor. The bottleneck is the Claude API's concurrency, never the queue.

Where overload hits first, and the lever already in place

The 2026-08-22 architecture review ranked the hotspots and named the lever for each. The levers are built; the review is archived. What survives is the order in which load will arrive, and the rung of the ladder that answers it.

HotspotSymptomLever
1AI researchRequests stuck in searching; 429s from the APIIts own queue and the store-first cache — a warm category never enqueues research at all. Then replicas of worker-research.
2Claude costThe bill moves before anything else doesModel tier per plan (cheap for Free and staff, best for paid), the translation memory, the 70-point AI confidence ceiling that keeps a cheap model from buying rank.
3PostgresSlow matching; connection exhaustion under web replicasAn index on every organization_id from day one; the big-store SQL prefilter for registry-sized tables; then pgbouncer, then a dedicated database VM — still local, never managed.
4SSR under trafficSlow time to first byteReplicate web behind the tunnel — it is stateless by rule, and the rate-limit counters already live in Redis so replicas share them.

The ladder, in order: web replicas → research-worker replicas → pgbouncer → dedicated database VM. Each rung is a compose change and none is a rewrite. A broker — RabbitMQ, Kafka — stays parked until a second application consumes events or Postgres measurably saturates; every enqueue passes through one seam, so that swap would be an adapter.

Part I · cited as ADR-001 §N

The demand-pull supplier graph

Two operating principles govern the whole supplier side:

  • Demand-pull, not supply-push. Nothing is spent on a supplier until a real request needs them; spend grows as a candidate approaches presentation.
  • The deal loop is the data-acquisition engine. Every facilitation produces capability, pricing and responsiveness data that cannot be scraped. That is the moat; everything scraped is bootstrap.

The supplier graph is the supplier table as node plus dated, sourced edges — source records, verification evidence, quotes, deals. Plain Postgres: "graph" is the shape, not the engine. The lifecycle lead → profiled → verified → engaged is derived from which edges a node has, never set by hand.

§1

No paid data providers, ever

enforced

A hard constraint on every future design (owner, 2026-08-26): no paid subscription to any data provider, now or later, and no design may align with one.

The customs and bill-of-lading investigation found no free route, so that data is closed. The consequence is honest rather than hidden: the export-record check is dormant, and tier-2 capability evidence has to come from certifications and the deal loop instead. New connectors are added only for genuinely free licensed sources.

§2

Sources have a role: discovery or verification

built

An axis orthogonal to dynamic/static, and the decision that makes registries pay for themselves without ever being enriched.

  • Discovery sources — today global_web alone — are workspace-selectable, and are the only sources that enter matching.
  • Verification sources — all registries — are platform infrastructure: never in workspace settings, never fed into matching. Buyers meet them only as evidence on a supplier profile: "Existence vérifiée — Registre du Québec, actif, consulté 2026-08".

Enforced in scope.ts, which resolves only role = 'discovery'. A supplier known only through a verification record is invisible to matching until a discovery source or the deal loop evidences it.

Registry stores are kept as local lookup tables, refreshed by full pull roughly every six months per source. Coverage expands on demand: when discovery surfaces candidates from an uncovered country, that is the trigger to add its registry. Where no registry route exists — China — tiering falls back to documents collected at facilitation time.

§3

Enrichment is lazy, and store-sized batches do not exist

not built

Nothing is enriched ahead of demand. The roughly $12k store-scale enrichment gate that sank the previous strategy dissolves because registry records never need enrichment at all — they are evidence, not candidates.

No enrichment stage exists in the code today. Descriptions come straight from the discovery findings; there is no site-scrape pass. The design stands, the capability is absent.

§4

The verification battery, and the derived trust tier

3 of 6

Six checks were specified, each writing an evidence row — type, source, result, URL, checked_at. Three run automatically today.

②Digital identitySite alive, TLS, domain age, MX, domain ↔ name coherence.auto · 30 d

The tier is derived from evidence rows, never set. 0 unverified → 1 existence verified, the floor for a Top-N → 2 capability evidenced → 3 Vérifié OSI. A sanctions hit dominates everything: the candidate is flagged, not tiered. verification_status is a projection of the tier, not an input to it.

A ceiling that matters

AI-found suppliers are capped at confidence 70, so a confident-sounding model can never outrank an OSI-verified company. The cap is in the code, not in a prompt.

§5

Intake is structured, and the pool is bilingual

built

The structured form is the primary intake: category (required), product, material, certifications, quantity, lead time, details. Typed fields become criteria rows directly with source: "user" — nothing guessed.

The taxonomy is one canonical in-house tree mapped behind the scenes to HS headings, and it is a typed module, not a table, because it is code-adjacent data that evolves by commit. Node ids are stable and persisted on requests.

Search runs English-first and the pool stores both languages. Most of the manufacturing web is in English; criteria carry a value_en and suppliers a description_en, so a French request reaches English text and a later English buyer finds the supplier a French request discovered.

§6

The deal loop feeds the graph — the moat

accumulating

Response time, MOQ, lead time, price and the buyer's satisfaction score are exactly the outcomes nobody can scrape. They arrive as a by-product of Part II, not as a separate project — which is why the facilitation work and the data strategy are one record and not two.

Two fields protect that data at the source (2026-09-12): response time is measured from sent_at — when staff actually emailed the supplier — and falls back to the buyer's ask only when nobody stamped it, so OSI's own lag is not published as a slow supplier; and decline_reason separates no response (the strongest negative signal the platform owns) from declined and lost — the buyer picked someone else, which says nothing about the supplier.

Part II · cited as ADR-002 §N

The transaction dossier and the contract centre

OSI used to stop at report_ready: a ranked Top-N, a printable report, and then the product ended. The owner's brief asks for the rest of the cycle and states the intent plainly:

« donner l'impression qu'OSI orchestre la transaction complète, et non seulement la recherche de fournisseurs. »

§1

One dossier, three entities

spine built

A quote is the unit of facilitation. Asking a supplier creates a quote in requested; what comes back moves it to received with price, lead time, MOQ and terms; the buyer compares and accepts one, and that acceptance is the single event that creates the deal.

There is deliberately no entity between the match and the quote. The previous design put one there and it earned nothing: an engagement with no offer in it is a status with no content.

The buyer picks who is approached. They select from their Top-N and ask OSI to solicit. Nothing is ever solicited automatically — supplier ids are validated against the request's own matches, so a crafted payload cannot reach a company that was never presented.

No splitting. One accepted offer, one dossier; a buyer who wants two suppliers makes two requests. Enforced by a partial unique index, not an application check — two acceptances arriving together would both pass the latter.

Two repairs since (2026-09-12): a recorded price can be corrected while the quote is still received — a correction is not a transition — and a supplier who declined or never answered can be asked again, with that round's clocks reset. An answer already held is never thrown away.

§2

External parties are records, never users

built

« Le fournisseur n'a pas accès directement à la plateforme pour l'instant — le personnel gère l'interaction avec eux. »

So contract_party is a row describing a party, not a membership: it points at a supplier or an organisation when we have one, and otherwise carries a bare name and email. Same tombstone pattern as the audit journal — nullable references plus a name snapshot, so the record stays readable forever regardless of what happens to the row it referenced.

  • No party accounts, no guest sessions, no supplier login. The membership model and every tenancy guard stay exactly as they are.
  • The portal has exactly two audiences: the buyer in their own workspace, and OSI staff in the internal one.
  • Every external interaction is staff-mediated and outbound. OSI sends, OSI records what came back.
§3

Two signature mechanisms, split by who the party is

built
PartyMechanismEvidence recorded
Buyer · OSI
they hold accounts		 Signed in the platform. No vendor, no email round trip. user id + name snapshot, when, IP, user agent
Supplier · carrier
broker · inspector		 Manual upload. Staff send it, receive it signed, upload the countersigned PDF. who signed as stated, when, the document, and which staff member recorded it

The mechanism follows the party's role — not a setting, and not contract_party.user_id, which is null at draft time and would make every party external. Both paths write the same party row and the same event trail, so the n of m indicator and the "all mandatory signatures in" transition do not care which produced a signature.

The successor is not a vendor either

No e-signature vendor is bought. esign.ts is the seam for the external path only, and its one provider is manual. The intended successor is a private signing link — our own capability URL, emailed to a party with no account — kept for later and optional beside manual, not instead of it: some counterparties will always return a signed PDF by post, and a link that replaced upload would strand them.

§4

Signature evidence is permanent; the audit journal is not

built

audit_log is purged at three months. Signature evidence must be immutable. These cannot be the same store — so signature evidence lives on the contract's own rows, never purged and never cascaded away, while the journal keeps recording the operational actions around it. Two trails, two retention rules, on purpose.

"Never cascaded away" became true against workspace deletion only on 2026-09-12: a workspace carrying a contract or a deal is archived, never erased — it disappears from the product, every route redirects to a recovery screen, the owner restores it by signing in, and the archive is kept six years. A workspace with no financial trace is still destroyed outright. No foreign key changed.

§5

Required contracts are derived from the parties

built

A deal with a carrier needs a carrier agreement; one with a customs broker needs a brokerage mandate. That mapping is a pure function of which parties the deal has. Staff can add a contract the mapping did not predict; staff cannot silently miss one it requires.

Version 1 ships the two unavoidable types — the OSI↔client mandate and the buyer↔supplier order. Contract text is frozen at draft time and rendered in the request's language, not the reader's: a contract is a record of what the parties saw. Numbering is OSI-2026-0000, per-year sequential and platform-global.

§6 · §7

Documents, and money

documents · first slice

Documents are one typed table — kind, what it hangs from, a file, an issuer, a version — absorbing the stored PDF report. The first slice exists (2026-09-12): the document row over file, hung from a quote and/or a request, staff attaching a supplier's PDF or photo to an offer, a list naming and linking both sources, and a sweep that purges an orphan — row, file and bytes — 36 months after it loses both references. Ownership follows the paperwork: staff upload, the buyer's workspace owns it.

Still open: documents hung from a deal or a contract (the countersigned-contract upload still writes a file row directly), the fuller kind vocabulary — invoice, customs, bill of lading, each arriving with the phase that produces it — versions, and the stored PDF report.

Money is tracked, never moved. No payment processor, no escrow. Payment rows will be staff-entered records of things that happened elsewhere.

§8 · §9

Status machines, derived views, and staff powers as data

built

Every entity gets guarded transitions — an illegal transition throws rather than writing a state the machine forbids — and every change writes an event row. Timelines and dashboards stay pure read-models of the database.

The contract filters — Actifs, À signer, En attente, Complétés, Expirés — are derived views, never columns. Expiry is computed at read time from the échéance, with no scheduled job.

contracts.sign is a permission key the owner assigns per role, and custom staff roles beyond manager and accountant are built: roles are rows, the matrix is dynamic. The owner is never a row, and role granting stays owner-only, forever — or the matrix could lock out its own editor.

Where it stops, precisely

The deal table already carries satisfaction, reviewed_at, reviewed_by, review_comment, closed_at and closed_by, and the guarded ladder open → contracting → in_production → shipping → delivered → reviewed → closed is enforced. But transitionDeal has exactly one caller: sending a contract moves the dossier open → contracting. Nothing moves it after that.

So a dossier opens, advances one step when its first contract goes out, and then cannot progress — not because the machine is missing, but because no surface drives it. That is the honest shape of steps 14-16, and it is why commandes is the next real piece of work rather than a late polish.

Still unanswered

Open questions

  1. Bytes left behind by a non-financial deletion. Retention itself is answered — 36 months for an orphaned document, six years for an archived workspace — but destroying a workspace with no contract or deal still cascades its document and file rows away without passing through the sweep, so those bytes linger on the volume. The remote-versus-local storage backend is still deferred to an environment switch, to be discussed.
  2. Is the deal layer a plan dimension? Plans gate requests per day and suppliers returned only, so a free-trial workspace can currently reach contracts.
  3. Who updates production milestones? Every update is an email and then a manual entry — the real cost of "no supplier access". This blocks orders.
  4. Per-request enrichment budget — dollars or candidates, per plan tier? Moot until §3 exists, but it is the first question §3 raises.
  5. Supplier-claim flow timing — with the supplier-side space, or after the first facilitated deals?
  6. May OSI nudge a buyer who never picks suppliers, and is signature-before-deposit the right order?
  7. Keep or remove "Marquer comme envoyée" on a quote? The buyer's notification on a recorded offer already exists; the button is the outbound stamp that lets the response time measure the supplier's lag rather than OSI's (Part I §6). Removing it puts OSI's own lag back into the moat's headline number.
