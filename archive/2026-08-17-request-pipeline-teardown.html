The one thing to confirm

With AI_CHAT=false, no AI runs anywhere in this flow — not in the chat, and not in supplier search either. The pipeline is regex, arithmetic, and two sleep() calls.

The “recherche mondiale” that queries internet sources is the E4 research agent, and it isn’t built yet. No web-search provider is chosen, no research_runs table exists, and nothing in src/ makes an outbound HTTP call. That matches the backlog — E4 is unchecked — but not the impression the PLAN gives.

  3. 3

    Criteria parsingbuilt

    src/server/parse-criteria.ts:49

    Pure regex, in-process, zero tokens: material words, N bar, N m³/h, ISO/CE/ATEX codes, quantity, lead time. Capped at 8 rows; if nothing matches it stores the first 120 characters as other so the loop keeps moving.

    Worth knowing: these rows are written with source: "ai". That is a label the UI reads, not a record that a model was called — no model was.

  4. 4

    Enqueue, failure-tolerantbuilt

    src/lib/requests-fns.ts:222 · src/server/queue.ts:31

    The pg-boss enqueue sits in a try/catch that logs and swallows. If the queue is down the request still exists in received, and the worker’s sweep picks it up later. This is the right shape — the buyer never loses a submission to an infrastructure blip.

  5. 5

    The pipelinesimulated

    src/worker.ts:36 · STAGE_MS = 8000 at :19

    Resume-capable: it reads the request’s current status and picks up wherever it rests, so a re-run is safe. received → searching, wait 8 s, searching → validating, wait 8 s, validating → report_ready.

    During searching it calls the matcher once (skipped if matches already exist). During validating, nothing runs at all — the stage exists to give the UI a fourth step to draw.

  6. 6

    Matchingplaceholder

    src/server/matching.ts:22

    Loads every supplier row — findMany() with no filter, currently 12 seeded companies — scores them, writes the top 5 to match, and stamps the headline score on the request.

02The scoring formula

The whole of today’s “compatibility”, verbatim from matching.ts.

scoreSupplier(requestId, supplier)

compatibility = min(98, 62 + confidenceScore / 5 + (verified ? 6 : 0) − (risk high ? 8 : risk medium ? 3 : 0) + hash(`${requestId}:${supplier.id}`) % 14 )

The criteria are never read. scoreSupplier takes only the request id and the supplier row — request_criterion is not queried anywhere in this file. The parsed material, pressure and certifications shape the dossier the buyer sees, but they have no influence on who ranks first.

The hash term is a deterministic 0–13 jitter, so the same request always ranks the same way on re-runs. It is what makes the Top 5 look considered rather than sorted by confidence.

The “N fournisseurs analysés” figure on the dossier is the analyzed field of the matches.created event — the size of the supplier table at scoring time. Today it says 12.

03Crash recovery and the legacy state

The part of the worker that is genuinely production-shaped.

On boot and every 60 seconds, worker.ts:69 re-enqueues anything sitting in received, searching or validating that has not been touched for two minutes. A worker crash, a lost job, a container restart mid-pipeline — all self-heal.

analyzing is deliberately excluded from the sweep. It is the legacy pause state from before the pre-search AI stage was removed on 2026-08-05; those dossiers keep a manual “Lancer la recherche” button and are never advanced automatically. New requests never enter it.

The detail page polls rather than subscribing: while isInFlight(status) is true it calls router.invalidate() on an interval — $id.tsx:74. Progress renders at 10 / 45 / 75 / 100%.
